## Objective

Define Zankai CLI and runtime contracts for the user-requested Zankai Agents rebuild.

## Requirements

- Inspect existing scripts/team-*.mjs and retain existing zankai:* commands.
- Define Zankai command grammar, project configuration, session schema and module APIs before implementation.
- Distribution: installable npm CLI with `zankai init`, `zankai status` and `zankai --help`. Resolve packaged assets from module location and consumer writes from selected workspace. GitHub hosts source; npm publication is a separate release. Package name availability/ownership must be checked.
- Specify npm run zankai (wizard/menu), npm run status (dashboard), named-agent filtering and JSON output; local-only MVP, no npm publishing.
- Separate stable agent identity, run/session identity, task status and connection health. Specify untracked/stale handling, timestamps, concurrent writes and session collisions.
- Define explicit target workspace resolution: team-lib currently captures process.cwd(); avoid initializing the kit instead of the chosen project.
- Specify review-before-write, cancellation without mutation, safe existing-project preservation, no automatic dependency installation or provider launch.
- Use existing Node >=20 ESM .mjs conventions for MVP; propose significant dependencies to Team Lead before adding them.
- Clarify .team/ROUTING.md no-continuous-polling rule: user-opened dashboard may refresh local files only; no background AI polling.
- Define provider-neutral task claims, canonical coordination storage shared across worktrees, scope reservations, contract revision/base commit references, change requests and an integration queue for T-006.
- Define paired FE/BE tasks that become ready together after shared contracts integrate. Separate filesystem overlap, semantic incompatibility and runtime resource collisions.
- Specify atomic claim acquisition, duplicate dispatch rejection, stale claim recovery requiring explicit human action, and one designated owner for shared-file changes.
- Distinguish advisory task scope from enforced provider/filesystem permissions. Require changed-file scope auditing without claiming it prevents all writes.
- Preserve manual provider dispatch and explicit Team Lead approval for merges. Git worktree preparation must be explicitly invoked; without a Git repository/base commit report isolation unavailable.
- Define unique dev ports and isolated test database/resource assignments; no automatic destructive database provisioning.

## Acceptance criteria

- [ ] Contracts cover wizard, runtime, dashboard, copy compatibility and negative cases.
- [ ] No invented provider integrations, CLI flags, token/context telemetry or running-agent inference.
- [ ] Provide explicit implementation interfaces and sample records; handoff ready for dependent tasks.
- [ ] A worked FE/BE example demonstrates simultaneous readiness, isolated workspaces, shared contract revision, conflict reporting and human-controlled integration.
